CU CONSUMPTION→How operations are smoothed to prevent capacity peaks
Interactive vs Background Runs
How Fabric calculates capacity utilization to manage heavy workloads
🖱️ Interactive Operations
Short-duration, user-driven events
  • Workloads: Power BI reports, SQL queries, ad-hoc Notebook executions
  • CU Smoothing Window: **10 minutes**
  • Allows immediate spikes but requires rapid drop-off
⚙️ Background Operations
Long-duration, automated pipelines
  • Workloads: Data Pipelines, Dataflow Gen2 refreshes, scheduled Spark Jobs
  • CU Smoothing Window: **24 hours**
  • Spreads the compute cost evenly over 24 hours to prevent capacity throttling
⚠️
Exam Trap: If capacity limit is exceeded, Fabric first delays interactive queries, then rejects them (HTTP 430), and finally pauses background jobs. Rescheduling background jobs to off-peak hours distributes the 24-hour window load!

Starter Pools vs Custom Pools
Choosing the correct Spark compute configuration is a key exam theme
⚡ Starter Pools (Default)
Serverless Pre-warmed Compute
  • **Warm start:** Sub-second session activation
  • Auto-scales based on the capacity SKU size
  • Managed entirely by Microsoft Fabric
  • Preloaded with standard data science runtimes
Best for: Quick execution, standard workloads
🛠️ Custom Pools
User-defined Virtual Machines
  • **Cold start:** Session startup takes **1-3 minutes**
  • Configure exact Node Size (Medium, Large, X-Large)
  • Set exact min/max executor count limit boundaries
  • Pre-install custom dependencies and libraries
Best for: Heavy ETL, isolated memory needs

Spark Performance
OPTIMIZE SPARK→Fine-tune Spark settings to resolve resource failures
Optimizing Spark Execution Settings
🔄 Dynamic Allocation
Automatically scales executor count up or down depending on task volume.
  • Prevents idle executors from locking CUs
  • Enabled by default in Microsoft Fabric workspaces
Sizing Limits
Set **Max Executors** inside the pool boundaries to prevent a runaway job from consuming the entire capacity budget.
🚨 Resolving Spark Out Of Memory (OOM) Errors
If your jobs fail with memory limits, apply these tuning steps:
  • Driver OOM: Increase **Driver Node Size** (occurs during collect()).
  • Executor OOM: Increase **Executor Node Size** or decrease cores per executor to lower parallel task memory stress.

Exam Traps
DP-700 CAUTION→Monitoring & troubleshooting traps
Top 4 Optimization Exam Traps ⚠️
🚫
Trap 1: "Dataflow Gen2 consumption is interactive"
❌ WRONG. Dataflows are background operations smoothed over 24 hours. Power BI report rendering is interactive (10-minute smoothing).
🚫
Trap 2: "Starter pools have longer spin-up times than custom pools"
❌ WRONG. Starter pools have pre-warmed nodes with sub-second activation. Custom pools require cold boot (1-3 minutes).
🚫
Trap 3: "Check Capacity app to debug notebook code errors"
❌ WRONG. The Metrics app monitors resource cost/throttling. Find notebook syntax and execution errors in the Spark UI logs.
🚫
Trap 4: "Executor OOM requires scaling Driver"
❌ WRONG. Executor OOM requires scaling executor node memory or reducing tasks. Driver OOM requires scaling driver node memory. They are independent.
